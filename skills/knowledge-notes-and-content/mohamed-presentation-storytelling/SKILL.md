# Mohamed Presentation Storytelling

## When to Use

Use this when Mohamed asks for:

- a presentation or pitch deck
- a strategic deck for a project, product, or opportunity
- a sales-oriented narrative from existing notes
- “choose a valuable topic from what we already have”
- a stronger deck from a rough memo or draft

This skill is for **story, structure, and usable output** — not generic copy dumping.

## Core Rule

Do not start from a blank aesthetic or a random topic if Mohamed already has active projects.

First anchor in his live system, then choose the **highest-leverage active topic**.

Priority order for topic selection unless Mohamed overrides it:

1. capital / investment decision quality
2. agent operating system and memory infrastructure
3. knowledge / retrieval systems with product potential
4. revenue-oriented products or services
5. lower-priority explorations

## Topic Selection Rule When Mohamed Says “You Choose”

When Mohamed does not specify the deck topic and asks you to choose:

1. Check the live snapshot and active project notes.
2. Prefer the project that is both:
   - currently active, and
   - strategically valuable beyond one piece of content.
3. Do **not** choose a scattered or novelty topic just because it sounds exciting.
4. State the chosen project briefly and why it is the highest-value option.

Good pattern:
- choose an active operating system, product, or monetizable workflow
- avoid lightweight idea-vault fragments unless they clearly outrank current projects

## Deck Objective Selection

Before writing slides, decide which of these deck modes fits best:

- **Vision deck** — what the system is and why it matters
- **Sales deck** — problem, value, proof, deployment path, commercial angle
- **Founder / strategy deck** — thesis, wedge, sequencing, moat, risks
- **Client deck** — current pain, offered solution, workflow, outputs, next step

If Mohamed simply asks to “start” after choosing a topic, default to:

**Sales deck**

because it forces clarity around problem, value, proof, and rollout.

## Source Gathering Discipline

Build only from real project material when available:

- current snapshot
- project notes
- saved state notes
- execution plans
- asset inventories
- prior research notes

Do not invent traction, metrics, customers, or proof.
If evidence is thin, frame the point as:

- thesis
- opportunity
- proposed workflow
- next proof step

not as established fact.

## Narrative Standard

A strong Mohamed deck should usually answer these chapters in order:

1. what problem is painful enough to matter
2. why current solutions leave a gap
3. what the system does differently
4. why the approach is believable
5. what narrow starting wedge proves value fast
6. what already exists and reduces execution risk
7. what the rollout path looks like
8. what concrete output or decision the system enables

If the title sequence alone does not tell the story, the deck is not ready.

## Arabic Output Rules

When delivering Arabic deck content for Mohamed:

- keep Arabic first
- no English mixed inside Arabic lines
- keep technical English terms on their own line when necessary
- prefer clear Egyptian-professional language over formal-heavy prose
- keep each slide anchored to one main idea
- avoid memo-like bullet floods unless the slide is explicitly a checklist or matrix

## OpenDesign Usage Pattern

If a local OpenDesign repository or equivalent design-skill source exists, use it as **design doctrine**:

- fixed slide canvas
- chapter-driven titles
- slide-scale typography
- visual variety across slides
- no generic AI-deck tropes

Use its guidance for taste and composition even if you are not installing it as a plugin in the current runtime.

## Preferred Build Sequence

1. choose the highest-value topic
2. read the project context files
3. decide deck mode
4. write the full title sequence first
5. draft the slide narrative in markdown
6. upgrade to a presentable artifact
   - HTML deck by default when immediate local output is fastest
   - PDF or PPTX when explicitly requested
7. verify the artifact exists and is actually servable/openable

## HTML Deck Default

When speed matters and no format is forced, HTML is the best first artifact.

Use:

- fixed 1920×1080 slides
- one section per slide
- keyboard navigation
- local scaling for viewport fit
- clean executive styling, not startup gimmicks

## Verification Pattern

Before saying the deck is ready:

- confirm the file exists
- confirm size is non-zero
- count slides/sections
- verify the title is present
- if local browser file opening is blocked, serve the folder over a tiny local HTTP server and verify with an HTTP request

Important:
A blocked `file://` preview is not a deck failure. Fall back to local HTTP serving and verify there.

## Common Pitfalls

- choosing a shiny but low-leverage topic when Mohamed says “you choose”
- turning a deck into a long memo with slide numbers
- writing vague “future is now” slide titles
- claiming traction or proof not present in the notes
- over-designing before the story is tight
- stopping at markdown when Mohamed asked to start building for real
- treating a preview-tool failure as if the artifact itself failed

## Output Standard

The final handoff should include:

- the chosen topic
- the deck mode
- the output path
- what is verified
- the next strongest upgrade path

Prefer concise, usable delivery over design-theory explanation.
